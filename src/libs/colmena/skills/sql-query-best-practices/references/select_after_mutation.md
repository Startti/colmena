# SELECT after mutation

Two patterns to verify what a mutation did.

## ✅ Pattern A — Trailing SELECT (RECOMMENDED for sql_query)

```sql
INSERT INTO orders (user_id, amount) VALUES (42, 100);
SELECT id, created_at FROM orders WHERE user_id = 42 ORDER BY id DESC LIMIT 1;
```
Works with multi-statement semantics. The trailing SELECT is the only one whose rows you'll see.

## ⚠️ Pattern B — RETURNING (limited usefulness here)

```sql
INSERT INTO orders (user_id, amount) VALUES (42, 100) RETURNING id, created_at;
```
On a single-statement call this works and you get the inserted row(s) as output.

If you combine RETURNING with other statements in the same call, **the RETURNING output is discarded** (only the last statement's result is returned). Use Pattern A in that case.

## Use cases

### Confirm a new row's autogenerated fields
```sql
INSERT INTO users (email) VALUES ('a@b.com');
SELECT id, email, created_at FROM users WHERE email = 'a@b.com';
```

### Confirm UPDATE affected the right rows
```sql
UPDATE orders SET status = 'shipped' WHERE id IN (1, 2, 3);
SELECT id, status, updated_at FROM orders WHERE id IN (1, 2, 3);
```

### Confirm DELETE removed what you intended
```sql
DELETE FROM sessions WHERE expires_at < now() - INTERVAL '30 days';
SELECT count(*) AS remaining FROM sessions;
```
You can't see the deleted rows after the fact — confirm via the counter of what remains.

## Tradeoffs

| You want… | Use |
|---|---|
| The autogenerated ID/timestamp of an inserted row | Pattern A with a WHERE that uniquely identifies the row |
| To loop over inserted rows in the same call | Not possible — break up the work |
| To know how many rows the mutation affected | Pattern A with `SELECT count(*) WHERE …` matching the same filter |
