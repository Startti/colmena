Arquitectura del SQL Node — 3 Enfoques

Cómo estructurar el nodo, sus servicios y su integración con el DAG engine

A

Nodo Monolítico

Un solo archivo sql.rs que maneja todo: conexión, validación, critic, ejecución, inventario de funciones.

Pros

  • Simple de implementar inicialmente
  • Un solo archivo para entender todo el flujo
  • Menos indirección

Cons

  • Archivo enorme (~800+ líneas) — difícil de mantener
  • Rompe la arquitectura hexagonal del proyecto
  • No se puede testear el critic sin la BD, ni la validación sin el critic
  • El pool de conexiones queda atado al nodo
B

Nodo Delgado + Servicios (Hexagonal) ⭐ Recomendado

El nodo SqlNode es un orquestador delgado que delega a servicios especializados a través de traits (ports).

SqlNode (infrastructure/nodes/sql.rs)
  ├── SqlConnectionPort (domain/trait) → PgPoolAdapter
  ├── SqlValidatorPort (domain/trait) → StaticRuleValidator
  ├── SqlCriticPort (domain/trait) → LlmCriticAdapter
  └── FunctionRegistryPort (domain/trait) → PgRegistryAdapter

Pros

  • Sigue la arquitectura hexagonal existente
  • Cada servicio se testea independientemente con mocks
  • El pool se comparte via Arc — inyectado al crear el nodo
  • El critic LLM se puede mockear en tests
  • Fácil añadir drivers (MySQL) después — solo nuevo adapter

Cons

  • Más archivos iniciales (~5-6 archivos)
  • Más indirección — hay que navegar entre capas
C

Múltiples Tipos de Nodo

Nodos separados: sql_select, sql_mutate, sql_introspect, sql_function. Cada uno es más simple pero se configuran por separado.

Pros

  • Cada nodo es pequeño y enfocado
  • Permisos implícitos por tipo de nodo
  • Fácil de entender cada uno individualmente

Cons

  • El usuario configura 4 tools en vez de 1 — más verboso
  • Duplicación de lógica (conexión, validación) entre nodos
  • No mapea bien al modelo de permisos granulares — los permisos están en el tipo, no en la config
  • El LLM necesita decidir qué nodo usar además de qué SQL escribir

Opción B — Estructura de archivos

Archivos a crear/modificar
src/libs/colmena/src/dag_engine/

domain/
  ├── sql_ports.rs ← traits: SqlConnectionPort, SqlValidatorPort, SqlCriticPort, FunctionRegistryPort
  ├── sql_permissions.rs ← SqlPermissions struct, enums de operaciones permitidas
  └── sql_errors.rs ← SqlError enum (Blocked, ValidationFailed, ConnectionError...)

application/
  └── sql_execution_service.rs ← orquesta: validate → critic → execute → feedback

infrastructure/
  ├── nodes/sql.rs ← SqlNode impl ExecutableNode (delgado, delega al service)
  ├── sql_pool_adapter.rs ← PgPool via sqlx, statement_timeout, work_mem
  ├── sql_static_validator.rs ← reglas estáticas (regex/pattern matching)
  ├── sql_llm_critic.rs ← adapter que usa LlmCallUseCase para evaluar SQL
  └── sql_function_registry.rs ← CRUD sobre sandbox.function_registry
