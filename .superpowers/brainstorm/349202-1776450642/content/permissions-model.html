Modelo de Permisos Granulares para SQL Node

¿Qué nivel de granularidad necesitamos? Revisa las 3 capas propuestas y dime si sobra o falta algo.

Capa 1: Operaciones (qué tipo de SQL puede ejecutar)

R

SELECT (Lectura)

Consultas de lectura. El caso más común y más seguro.

C

INSERT (Creación)

Crear nuevos registros en tablas existentes.

U

UPDATE (Modificación)

Modificar registros existentes. Requiere WHERE obligatorio?

D

DELETE (Borrado)

Eliminar registros. ¿Requiere WHERE obligatorio? ¿Límite de filas?

Capa 2: Operaciones DDL (estructura de la BD)

+T

CREATE TABLE

Crear tablas nuevas. Caso raro pero útil para agentes que gestionan su propio esquema.

~T

ALTER TABLE

Modificar estructura de tablas existentes. Alto riesgo — puede romper aplicaciones.

-T

DROP TABLE

Eliminar tablas completas. Destructivo e irreversible.

IX

CREATE/DROP INDEX

Gestionar índices. Menos destructivo pero puede afectar rendimiento.

Capa 3: Introspección (leer la estructura de la BD)

LT

Listar Tablas

Ver qué tablas existen. Esencial para que el LLM sepa dónde buscar.

DT

Describir Tabla (columnas, tipos)

Ver estructura de una tabla específica. Necesario para generar SQL correcto.

LS

Listar Schemas

Ver schemas disponibles (public, analytics, etc.).

EX

EXPLAIN (plan de ejecución)

Ver cómo PostgreSQL ejecutará una query. Útil para optimización.

💡 Pregunta clave

Selecciona en cada capa los permisos que crees que deben existir como opciones configurables (no cuáles estarían activos por defecto — eso lo decidimos después).
