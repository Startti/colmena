Critic Híbrido: Reglas Estáticas + LLM

Cómo funcionan las dos capas en conjunto — ejemplos reales con PostgreSQL

Capa 1: Reglas Estáticas (siempre activas, instantáneas, gratis)

Análisis de texto/patrones sobre el SQL. No necesita LLM. Responde en <1ms.

Ejemplo 1 — BLOQUEADO por regla estática
Agente genera →
DELETE FROM production.orders
❌ Regla: "DELETE sin WHERE" → BLOQUEADO
Respuesta al agente: "DELETE requires a WHERE clause. Reformulate your query specifying which rows to delete."
Ejemplo 2 — BLOQUEADO por regla estática
Agente genera →
DROP TABLE production.users CASCADE
❌ Regla: "DROP TABLE no permitido" → BLOQUEADO
Respuesta al agente: "DROP TABLE is not allowed. You can only create/drop objects in the sandbox schema."
Ejemplo 3 — ADVERTENCIA por regla estática
Agente genera →
SELECT * FROM production.orders WHERE status = 'pending'
⚠️ Regla: "SELECT * detectado" → EJECUTA con advertencia
Feedback al agente: "Prefer selecting specific columns (id, total, status) instead of * to reduce data transfer."
Reglas incluidas:
  • DELETE / UPDATE sin WHERE → bloqueo
  • DROP / TRUNCATE / ALTER en schema protegido → bloqueo
  • SELECT * → advertencia
  • Queries con más de N JOINs → advertencia
  • Operación no permitida por config de permisos → bloqueo
  • Acceso a schema no autorizado → bloqueo

Capa 2: Critic LLM (opcional, configurable, ~1-3s extra)

Un segundo LLM analiza el query DESPUÉS de pasar las reglas estáticas. Solo se activa si guardrail_llm: true.

Ejemplo 4 — Query pasa reglas estáticas pero el LLM detecta problemas
Agente genera →
SELECT o.id, o.total, c.name, c.email
FROM production.orders o
JOIN production.customers c ON c.id = o.customer_id
WHERE o.created_at > '2024-01-01'
ORDER BY o.total DESC
✅ Reglas estáticas: OK (columnas específicas, tiene WHERE, schema permitido)
⚠️ Critic LLM dice:
Seguridad: ✅ OK — solo lectura, schemas permitidos
Optimización:
• Añade LIMIT — sin él puede retornar millones de filas
• La columna orders.created_at debería tener un índice para este filtro
• Considera añadir un índice parcial: CREATE INDEX idx_orders_recent ON orders(created_at) WHERE created_at > '2024-01-01'
→ EJECUTA con feedback de optimización adjunto
Ejemplo 5 — Query pasa reglas pero LLM detecta riesgo sutil
Agente genera →
UPDATE production.orders
SET status = 'cancelled'
WHERE customer_id IN (
  SELECT id FROM production.customers
  WHERE last_login < '2020-01-01'
)
✅ Reglas estáticas: OK (UPDATE tiene WHERE, schema permitido, UPDATE habilitado)
❌ Critic LLM dice:
Seguridad: ❌ RIESGO ALTO
• Este UPDATE afecta potencialmente miles de filas en producción
• Cancelar pedidos por inactividad del cliente es una decisión de negocio que necesita revisión humana
• Recomendación: ejecutar primero como SELECT COUNT(*) para ver cuántas filas se afectarían
→ BLOQUEADO — el critic tiene poder de veto sobre seguridad
